# Prepared only: bounded native Standard stability test

No executable or window has run for this new fixture. It typechecks locally with Swift5.9.2/SDK14.2 targeting arm64/macOS13. No product source is linked or changed.

The two320×180point atlas images use the same normally decoded namedPQ CGImage and NSImage logical size320×180: native NSImageView and bare native SwiftUI Image. A plain flipped AppKit parent holds the688×240 SwiftUI host and a separate visible192×108 ToneView sibling. The sibling reuses the successful Annex5 prototype's ToneMap.swift byte-for-byte and its Display.swift rendering/potential-headroom policy; Display changes add only draw/commit/completed-command diagnostics, shown in Display.diagnostic.patch. This is a fixture driver and does not make that candidate formula a product rule.

The accessory app uses a NonKeyWindow and orderFrontRegardless so its small driver can be visible while the startup foreground remains unchanged. It calls neither activate nor makeKey, changes no user preference/brightness/wallpaper, and stops on inactive/nonkey/foreground/visibility/frame violations. The collection deadline is7.2seconds; a process-only7.9second watchdog leaves hard-deadline.txt and exits124 if the main thread cannot finish. Normal cleanup stops the driver/observers, releases NSImageView images, detaches views and closes only its own window. A watchdog exit is incomplete evidence, not a successful run.

Every poll retains current/potential headroom, driver requested flag/visible rectangle/attachment/drawable size/draw count, window/app/foreground state and readback count. Driver GPU submissions/completion statuses and original completed float16 readbacks are retained, as are genuine OS screen notifications. Current1→approximately potential→1 each requires two headroom-ready observations, but **no image equality gate exists**. Each accepted capture saves the original window PNG, actual headroom before/after and the two actual image ROIs/canonical hashes. Any image change is data, not a reason to discard that stage. `success` means the phase collection finished, not that Standard stayed constant. Offline ICC normalization must compare all10patches and gray ramp across the phases and both components.

The two images do not actively set an EDR flag. Their appearance constancy under someone else's actual currentHd>1 is the question. WindowServer SDR captures alone cannot establish physical panel brightness or inspect private native image linear buffers. Even a complete constant screenshot result is limited to these assets, window/display/OS state and current headroom; it is not arbitrary Standard/High, metadata/HLG/alpha/EXIF or macOS14 equivalence.

# Prepared only: protocol-PQ derived display copy

This work directory contains two independent Swift entry points. No product files, source images or ICC profiles were edited. No Swift typecheck/build, offline CGImage decode or UI run has been executed for these new sources. Only the existing source-file hashes and syntax are checked at preparation time; this is not new runtime evidence.

`PQCanonicalCore.swift` follows the current Runtime helper's native recognition and strict CICP guard verbatim in operation (12bytes/type/reserved/RGB/9/(16or18)/0/1 and the macOS14 availability boundary), then accepts only a PQ result. Native namedPQ keeps the original CGImage. Only an unrecognized source whose complete strict CICP proof selects canonicalPQ receives `copy(colorSpace:)`. It retains the original decoded image, original source file data, ImageIO source/properties, ICC and provider data separately. There is no CGContext/CoreImage redraw, tone formula, reference-white scale or metadata rewrite.

`Offline.swift` imports no AppKit, SwiftUI or MetalKit. When root chooses to execute that small entry, its report checks original-file/ICC and EXIF-orientation preservation, derived dimensions/bits/rowstride/bitmapInfo/alphaInfo/byteorder/interpolation and provider bytes, then compares custom derived raw layout/bytes/orientation to the named source's original normal ImageIO decode. Display orientation is carried separately; color-space copying does not bake it into pixels. Existing opaque EXIFup inputs do not establish other EXIF/alpha behavior. The actual existing custom filename is source-ffb-icc.png, not a newly generated source-ffb.png. `input-manifest.json` records the exact existing paths/hashes.

`UICandidate.swift` is a separate later entry using the same core. Its two targets are both bare SwiftUI Image: the custom-derived candidate and the original native namedPQ oracle. Both have original rendering mode and320×180point frames. It accepts only the existing EXIFup pair, so there is no inferred orientation/alpha matrix. The plain-parent, visible nonkey192×108 driver, full headroom/GPU trajectory and7.2second collector/7.9second own-process watchdog reuse the successful minimal fixture. ToneMap.swift and Display.swift are symlinks to its archived sources, avoiding duplicate driver copies. No NSImageView target remains. There is no image-equality capture gate. Source preservation/offline invariants run before the UI entry creates a window.

Root will choose any offline build or one UI execution time. Build the offline entry with PQCanonicalCore.swift+Offline.swift only. Build the UI entry with PQCanonicalCore.swift+UICandidate.swift+ToneMap.swift+Display.swift, excluding Offline.swift. Use a separate bounded module cache/output and delete it after hashing if built. Inputs are the retained color-probe13/source-named-pq.png and source-ffb-icc.png; the UI additionally receives the existing showcase/images/hdr-pq.png neutral driver fixture. Use a fresh output directory.

The first UI question is only whether a protocol-PQ color-space-only copy reproduces the existing namedPQ native baseline while the original caches/data stay intact. Actual13 namedPQ still differs from14 normal color samples (cool812 red≈92.49vs119 in the previously measured complete pipelines); no formula is tuned to that atlas. HLG, hero snapshots, other EXIF/alpha, gain-map HDR and whole Bern layout/product acceptance remain untested boundaries.
